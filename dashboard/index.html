About

Why another recovery bot?

Most recovery agents optimize for one number: how much did it retry. Vasuli optimizes for three things at once, and refuses to trade one for the others silently.

01

Explainable

Every decision carries its root cause, confidence score, and the exact rule checks that approved or blocked it — visible in the audit trail, not buried in a model's weights.

02

Compliance-bound

AFA thresholds and pre-debit notice windows, modeled from public RBI/NPCI reporting, are enforced in deterministic code the LLM cannot override.

03

Honestly measured

The backtest engine reports net recovered revenue after outreach cost — including the uncomfortable finding that the compliant policy earns less, on the record.

Product

How a recovery decision actually happens

Four stages, one narrow LLM call, one deterministic gate before any money action.

1

Detect

Unresolved failed-mandate and abandoned-checkout events are flagged from the batch.

2

Diagnose

Claude reads the raw gateway error text and returns only a root cause label and a confidence score.

3

Decide

A deterministic rules engine checks compliance and caps, then picks the cheapest valid channel.

4

Execute & log

Only an approved action runs. Every stage is written to an append-only audit log.

Cost-aware channel ladder

Auto-retry before email, email before WhatsApp, WhatsApp before a paid human escalation.

Hard stopping rules

Three attempts, then straight to an honestly reported exception list — no infinite retries.

Graceful degradation

No API key or a failed LLM call falls back to a conservative heuristic instead of crashing.

Policy backtesting

Replay the same batch under alternate policies and see the real ₹ cost of every trade-off.

How a merchant actually uses this

In production, a merchant connects their Razorpay account once. From then on, Vasuli runs unattended: every time Razorpay fires a payment.failed or subscription.halted webhook, it lands directly in the detection layer below — no dashboard visit required. The merchant simply checks back later to see how much was recovered, and drills into any single case if they want to know why.

The live demo in the next section replays that exact same pipeline against a 55-event synthetic batch, since this build runs in Razorpay test mode rather than against a live merchant's real transaction stream. The "Run recovery batch" button stands in for what a webhook would otherwise trigger automatically.

Architecture

Three decisions worth defending

The design choices below are what make Vasuli explainable and bounded rather than just another retry loop — each one is deliberate, and each one trades something off.

Decision 1

The LLM only parses text. It never decides.

What it does: Claude reads one thing — the raw, unstructured gateway error string (e.g. "NPCI Error: Insufficient Balance (Code: 51)") — and returns a root_cause label plus a confidence score. Nothing else.

Why: Gateway error text is genuinely unstructured and varies by bank/PSP — a real text-classification problem, which is what LLMs are good at. Every decision after that (retry or not, which channel, what it costs) is deterministic Python in app/rules/. A wrong LLM output can produce a wrong label; it can never produce a wrong money action, because the rules engine re-validates everything independently.

Trade-off: this means Vasuli can never use the LLM for anything cleverer — no LLM-driven negotiation, no LLM picking the channel. That ceiling is intentional.

See: app/diagnosis/llm_parser.py
Decision 2

Compliance rules sit between the LLM and any action.

What it does: Two rules, modeled from public RBI/NPCI e-mandate reporting — an ₹15,000 Additional Factor of Authentication threshold, and a 24-hour pre-debit notice cooldown — are enforced as plain if statements, not prompts.

Why: A rule an LLM is merely "instructed" to follow can be argued around by a confusing enough input. A rule enforced in code cannot. tests/test_rules.py proves this: it feeds the rules engine a maximally confident, wrong diagnosis and shows it still refuses to silently retry above the threshold.

Trade-off: the rules are illustrative approximations of public reporting, not a verified legal compliance product — stated plainly in the README rather than overclaimed.

See: app/rules/compliance.py, app/rules/channel_selector.py
Decision 3

The backtest reports the uncomfortable number too.

What it does: backtest/run_backtest.py replays the same 55-event batch under two policies. The aggressive policy nets ~21% more revenue — by skipping the pre-debit cooldown. Vasuli still ships the compliant policy as default.

Why: A backtest that only ever proves your own default policy wins isn't measuring anything — it's confirming a decision that was already made. Reporting the trade-off honestly, including the cost of staying compliant, is closer to what the brief's "honest metrics" bar is actually asking for.

See: backtest/policies.py, backtest/backtest_report.md

Anticipated questions

Why not let the LLM pick the channel directly?
Because a channel choice is a money action, and money actions need to be testable without needing an API key or dealing with model non-determinism. tests/test_rules.py runs 8 assertions on the decision logic with zero LLM calls.
What happens if the LLM call fails entirely?
llm_parser.py falls back to a keyword heuristic and lowers its own confidence, which makes the rules engine route to human escalation instead of guessing. The whole pipeline runs end-to-end with zero API keys set.
Is the RBI/NPCI compliance modeling verified?
No — it's built from public reporting for demo purposes, and the README says so explicitly. The point being demonstrated is hard-coded compliance as a pattern, not a certified legal product.
